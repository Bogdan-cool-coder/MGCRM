# SpaceCRM: отчёты и планирование — анализ и маппинг на MGCRM (2026-07)

> Источник: живое исследование spacecrm.ru (аккаунт юзера, план «MACRO Global», интеграция с amoCRM) — 6 заданных страниц + бонус-вкладка «Прогноз». Read-only: скриншоты, текст страниц, DOM-инспекция без единого клика по действиям.
> Сверка с кодом: `src/app/Domain/{Sales,SalesPulse,Activity}` + `front/src` (инвентаризация от 2026-07-03).

---

## 0. Общая рамка модуля планов SpaceCRM (важно для понимания всех страниц)

- **Один «План» = именованный контур планирования** («План "MACRO Global"»), привязанный к интеграции amoCRM (`/plans/amocrm/<view>/<planId>/`). Глобальные контролы: селектор **месяца** и **года**, кнопка ручной синхронизации (⟳) и «Настройки AmoCRM».
- **Два слоя планов**: `plan_type=operative` (**Оперативный** — пересматриваемый) и **Годовой** (фиксированный). Переключатель есть на «Задачах», «Конверсиях», «Поступлениях», «Графике».
- **Ввод планов — inline в План-ячейках матриц** (на «Закрытии задач» DOM содержит 216 `<input>` в таблице: план на сотрудника × месяц × тип задачи; на «Поступлениях» — план на продукт × месяц). Никакого отдельного «мастера планирования» — план вводится прямо в отчёте.
- **Факт — только из amoCRM** (сделки, бюджеты, задачи), обновляется синком; live-обновления нет.
- **Вкладки одного плана**: Задачи (`completed-tasks`) · Конверсии (`conversions`) · Темпы продаж (`sales-performance`) · Поступления (`new-income`) · Подписка (`subscription-balance`) · Реестр подписки (`subscription-registry`) · Прогноз (`income-forecast`) · График (`income-forecast-schedule`) · Реестр (`expected-deals`).
- **Экспорт**: у таблиц — «Скачать как PNG» / «Копировать в буфер» (не Excel!).
- Разрез «по менеджеру» есть в задачах/конверсиях; денежные планы — в разрезе **продуктовых линеек** (CRM/ERP/BANK/SALES), не менеджеров.

## 1. Каталог исследованных отчётов

### 1.1 Реестр ожидаемых сделок/поступлений — `/plans/amocrm/expected-deals/7/`

**Что показывает.** Помесячный операционный реестр «денег в пути», две таблицы:
1. **«Ожидаемые поступления»** — открытые сделки с датой оплаты в выбранном месяце. Колонки: Сделка (ссылка) · Ответственный · Тип (Прямая/СБС) · Продукты (теги позиций) · К оплате (₽) · Факт (₽) · Дата оплаты · Договор подписан (дата) · **Результат последней задачи** (текст последнего комментария/задачи + timestamp) · строка Итого.
2. **«Дожим»** — те же колонки, но сделки, у которых ожидаемая дата оплаты **уже проехала/горит** (slippage-очередь: «оплата ожидается в пт», «ждём оплату до 15/07»). Итого по дожиму: 3 943 765 ₽.

**Планирование.** Прямого ввода плана нет — это факт/прогноз-реестр; «плановость» в самих сделках (дата оплаты, сумма). Фильтр «Тип учёта: Фактический/Плановый».
**Фильтры**: продуктовая линейка (CRM/ERP/BANK/SALES/Все) · тип сделки (Прямая/СБС/Все) · тип учёта · ответственный (multi-select).
**Факт-источник**: сделки amoCRM (бюджет, кастом-поля дат оплаты/подписания, последняя задача).
**Визуализация**: таблицы, экспорт PNG.

### 1.2 План выполненных задач — `/plans/amocrm/completed-tasks/7/`

**Что показывает.** «Закрытие задач»: годовая матрица **План/Факт/%**. Строки — группы: «Все задачи» + по каждому **типу задачи** amoCRM (3.4 Schedule, 4.1 MeetingDone✅, 6.1 Proposal✅, 7.1 Contract✅, 8.1 Success✅), внутри каждой — разбивка по сотрудникам. Колонки: «Всего» + 12 месяцев, в каждом триплет План · Факт · %. Цветовая заливка % (зелёный/жёлтый/красный).

**Планирование.** ⭐ Ядро механики: план вводится **inline в ячейку** — количество задач данного типа на **сотрудника × месяц** (216 инпутов в DOM). Слои Оперативный/Годовой.
**Факт-источник**: закрытые задачи amoCRM, сгруппированные по типу задачи и исполнителю.
**Визуализация**: одна плотная сводная таблица, без графиков.

### 1.3 План конверсий — `/plans/amocrm/conversions/7/?plan_type=operative`

**Что показывает.** Матрица **План/Факт/%** по конверсиям (те же 12 месяцев + Всего). Три блока:
- **Общие** — авто-пары «тип задачи / Все задачи» (доля MeetingDone от всех задач и т.п.).
- **Настраиваемые** — юзерские пары «числитель/знаменатель» (Презентация/КП, Презентация/Договор, Презентация/Сделка), с иконками ✏️/🗑 и кнопкой **«Добавить конверсию»** — конструктор метрик.
- **По сотрудникам** — те же настраиваемые пары в разрезе каждого менеджера.

**Планирование.** План конверсии — **производный** от планов числителя/знаменателя (вводятся на «Задачах»); % = факт-конверсия / план-конверсия. Конверсии — по **количествам задач**, не по стадиям воронки (стадийных конверсий из истории сделок у SpaceCRM на этом экране нет!).
**Факт-источник**: те же закрытые задачи amoCRM (+ сделки для пар вида «Презентация/Сделка»).
**Визуализация**: таблица с цветовой индикацией, значения в %.

### 1.4 План новых поступлений — `/plans/amocrm/new-income/7/?plan_type=operative`

**Что показывает.** Деньги: строки — **продуктовые линейки** (CRM/ERP/BANK/SALES, руб.) + ИТОГО; колонки на каждый месяц — двойная группа:
- **Прогноз**: `План` (ввод) · `Ожидаемое` (открытые сделки с датой оплаты в месяце) · `Всего` (факт+ожидаемое) · `%` (Всего/План);
- **Поступления**: `Факт` · `%` (Факт/План).

**Планирование.** ⭐ План денег вводится inline на **продукт × месяц** (не на менеджера!). Слои Оперативный/Годовой.
**Факт-источник**: поступления по сделкам amoCRM, атрибуцированные к продуктовой линейке основного продукта сделки.
**Визуализация**: таблица; горизонтальный скролл по 12 месяцам.

### 1.5 График прогноза поступлений — `/plans/amocrm/income-forecast-schedule/7/`

**Что показывает.** «График НП»: **календарная матрица дней месяца** (1–31 + Итого). Строки: Прямая · СБС · Всего · **Накопительно** (кумулятив) · **Распределение**. В ячейках — суммы, ожидаемые/пришедшие в этот день. Легенда цветов: 🟩 плановые поступления · 🟨 дожим · ⬜ фактические · 🟥 выходные.

**Планирование.** Ввода нет — рендер дат оплат сделок по дням; «Распределение» размазывает суммы без даты.
**Факт-источник**: те же сделки (дата оплаты/факт оплаты) из amoCRM.
**Визуализация**: heat-таблица по дням; идеальный кандидат на ECharts-календарь/бар.

### 1.6 (бонус) Прогноз поступлений — `/plans/amocrm/income-forecast/7/`

Сводка помесячного прогноза: на продукт × тип сделки — `План` · `Мин.порог` · `Факт` · `Выполнение %` · `Ожидаемое` · `Дожим` · **`Прогноз` = Факт + Ожидаемое + Дожим** · `Прогноз выполнения %` · `Прочее` · `Прогноз+Прочее` · `След. месяц` (хвост, уезжающий на следующий месяц). Кнопка «Показать партнёрские». Формула прогноза — чисто аддитивная, **без взвешивания вероятностями стадий**.

### 1.7 Отчёт «Лучший менеджер» — `/sales/reports/best-manager`

**Что показывает.** Годовой геймифицированный рейтинг менеджеров: # (топ-3 с медальками) · Менеджер · Всего · Достижения · Сделки · Сопровождения · Новые поступления (₽) · Средний чек (₽) · **Очки НП** · **Очки итог** · Дивизион (Россия/Глобал). Внизу — карточка «Лидер» (имя, дивизион, сделки, очки, поступления). Тумблер **«Стандартный / Абсолютный» зачёт** (сотрудники вне зачёта помечены «—»: Admin, ушедшие). Переключатель года.

**Планирование.** Нет — чистый рейтинг. Очки начисляются по правилам (за НП, за сделки/сопровождения); механика конфигурируется вне страницы.
**Факт-источник**: сделки + поступления amoCRM за год.
**Визуализация**: таблица + hero-карточка лидера; графиков нет.

## 2. Маппинг на наш код: из чего собирается каждый отчёт

Ключевая находка: **фундамент почти целиком уже есть.** `Deal` уже несёт все нужные даты: `expected_payment_date`, `expected_sign_date`, `expected_close_date`, `signed_at`, `paid_at`, `kp_sent_at`, `contract_sent_at` (`src/app/Domain/Sales/Models/Deal.php`). Activity имеет `kind/completed_at/responsible_id/result_text`. Деньги — копейки + `ExchangeRateService` (FX). RBAC-видимость — `VisibilityScope` во всех агрегаторах.

| # | Отчёт SpaceCRM | Что уже есть у нас | Что достроить | Оценка |
|---|---|---|---|---|
| 1 | **Реестр ожидаемых поступлений + Дожим** | `Deal.expected_payment_date/paid_at/signed_at`, `DealProduct` (продукты), `Deal::nextTask()`/Activity `result_text` (результат последней задачи), `DealExportService`-паттерн, item-level scope | Сервис `ExpectedIncomeRegistryService` (2 запроса: expected в месяце / expected < today && !paid), API + экран-таблица (2 DataTable) | **S/M** (BE — S, FE — S) |
| 2 | **Закрытие задач (план/факт по типам)** | `Activity.kind/completed_at/responsible_id` — факт агрегируется одним query; `ActivityService::countFtmForUser` как образец | Таблица планов `plan_targets` (universal: metric_kind, scope_type/scope_id, period_year/month, value) — у `SalaryPlan` только income+FTM; матричный экран с inline-вводом плана (у нас уже есть inline-edit паттерны PrimeVue) | **M** |
| 3 | **Конверсии (вкл. настраиваемые пары)** | Факты: Activity counts + `DealStageHistory` (ستадийные конверсии — у нас ЛУЧШЕ источника SpaceCRM); `SalesDashboardService::funnelMetrics` уже считает transition % | Сущность `conversion_defs` (числитель/знаменатель: тип задачи | стадия | событие), расчёт план-конверсий из plan_targets, экран-матрица | **M** |
| 4 | **Новые поступления (план денег по продуктам)** | Факт Phase A: `WonDealsFactSource`/`ManagerKpiService::personalIncomeFact` (won, FX-нормализация); продуктовая размерность: `DealProduct`→`Catalog.Product`; «Ожидаемое» = open deals по `expected_payment_date` | План на продукт×месяц (тот же `plan_targets`, scope=product_line), группировка поступлений по линейке, экран; Phase B факт-платежи = Finance (greenfield) — уже заложен `PaymentsFactSource`-стаб | **M** (L с Finance) |
| 5 | **График НП (день-календарь)** | Все данные из #1/#4 (те же сделки+даты); ECharts подключён | Чистый рендер: heat-таблица дней/кумулятив (можно ECharts custom или PrimeVue DataTable) | **S** (после #1) |
| 6 | **Прогноз (Факт+Ожидаемое+Дожим)** | `SalesDashboardService::forecastData` (взвешенный по вероятностям — у нас УЖЕ умнее аддитивного SpaceCRM); дожим-очередь из #1 | Свести обе модели в один экран: аддитивный «денежный» прогноз + weighted-прогноз рядом; «Мин.порог» = поле plan_targets | **S/M** |
| 7 | **Лучший менеджер (очки, зачёты)** | `SalesDashboardService::topManagers`, `ManagerKpiService::teamKpiBatch/teamRank`, средний чек тривиален; дивизион = `Org.Department` | Конфиг очков (points rules — по духу похоже на `TeamKpiRule`), годовая агрегация, экран-рейтинг с hero-карточкой | **S/M** |

**Сквозное недостающее звено — единая таблица планов** `plan_targets` (метрика × скоуп × период, два слоя operative/annual). Всё остальное — агрегация над существующими моделями + экраны.

## 3. Рекомендация по размещению

**Вердикт: строим в `Domain/Sales` (суб-неймспейс `Sales/Reports` или `Sales/Planning`), НЕ создаём standalone `Domain/Analytics` сейчас.**

Почему:
1. **Все факт-источники — модели Sales/Activity** (Deal, DealProduct, DealStageHistory, Activity). Аналитика у нас по аудиту «вшита в Sales», и оба зрелых агрегатора (`SalesDashboardService`, `ManagerKpiService`) уже там — новые сервисы отчётов встают в тот же паттерн single-aggregator + VisibilityScope.
2. **Планирование обязано жить рядом с мотивацией.** У нас уже ЕСТЬ план-контур: `SalaryPlan` (менеджер×месяц: деньги+FTM), `TeamTarget` (департамент×месяц), `MotivationCard`/`TeamKpiRule` (пайплайн×месяц). SpaceCRM-планы — это те же оси. **Нельзя плодить второй контур**: вводим `plan_targets` как обобщение (metric_kind: `income_money` | `tasks_by_type` | `conversion_pct` | `ftm`; scope: user / department / product_line / pipeline; слой: operative/annual), а `SalaryPlan.personal_income_plan_kopecks` и `TeamTarget` либо мигрируют в него, либо объявляются его частными случаями — решение за backend-architect на спеке. МК-конструктор тогда читает план из единого источника (сейчас `salary_plan_kopecks` уже линкуется в items — шов готов).
3. **Выделение `Domain/Analytics`** оправдается, когда появятся кросс-доменные отчёты (CS + Финансы). Тогда `Sales/Reports` переезжает механически — сервисы уже будут изолированы.

**Навигация** (`front/src/shared/nav/navItems.ts`): новая группа **«Отчёты»** в сайдбаре: Дашборд (существующий) · **Планы** (страница-оболочка с вкладками, как у SpaceCRM: Задачи / Конверсии / Поступления / Прогноз / График / Реестр) · **Лучший менеджер**. Manager Cabinet и МК остаются как есть (личный кабинет ≠ отчёты руководителя). RBAC: `view-sales-reports` (admin/director/cfo) + режим Own для менеджера на своих строках.

**Порядок сборки** (вертикальными срезами): (1) Реестр+Дожим — S/M, самый быстрый wow; (2) `plan_targets` + Закрытие задач — M; (3) Поступления по продуктам + Прогноз + График — M; (4) Конверсии (пары-конструктор) — M; (5) Лучший менеджер — S/M.

## 4. Что мы сделаем лучше SpaceCRM (наши козыри)

1. **Realtime вместо ручного синка.** У SpaceCRM факт обновляется кнопкой-рефреш из amoCRM. У нас факт рождается в той же БД + **Reverb live** — план/факт/дожим обновляются в момент закрытия сделки/задачи, без кнопки.
2. **Единый контур план → факт → зарплата.** У SpaceCRM планы «живут отдельно» от мотивации. У нас `plan_targets` ↔ `MotivationCard` (live-прогноз бонуса, gate ≥80%, 60/40 split) — менеджер видит, как выполнение плана конвертируется в деньги в кармане. Ни один из конкурентов этого не даёт в одном экране.
3. **Настоящие воронковые конверсии.** SpaceCRM считает конверсии по соотношениям задач. У нас `deal_stage_history` (append-only) — стадийные конверсии + скорость прохода + причины потерь (`LostReason`) как второй, более честный слой поверх task-конверсий.
4. **Умный прогноз двух моделей.** Их прогноз аддитивный (Факт+Ожидаемое+Дожим). Мы показываем его РЯДОМ с нашим взвешенным по вероятностям стадий (`forecastData`) + трекинг точности прогноза по прошлым месяцам (forecast accuracy).
5. **Мультивалюта.** SpaceCRM — только ₽. У нас FX-нормализация (`ExchangeRateService`, `FxRate`) с `multi_currency_warning`.
6. **RBAC-видимость.** У них план виден всем, у нас scope All/Department/Own на каждом агрегате (менеджер видит себя и команду — не чужие деньги).
7. **Каналы доставки.** SalesPulse уже шлёт Telegram-дайджесты план/факт — те же метрики отчётов поедут в утренний пульс без доп. работы; экспорт xlsx (`buildXlsx`-паттерн) против их «Скачать как PNG».
